# Dead-code map for code caves

> **Status · Updated to match `validate_cave_layout()` (`core/core_patches.py`)**
> Dead-function scan generated by `tools/dead_code_map.py` — rerun the tool
> before carving new regions. Static evidence is *not* proof: any unvalidated
> candidate must first survive a `brk #0` trap build (`tools/lab_trap_apk.py`)
> on device, and every new allocation must be added to `validate_cave_layout()`.

## Why this exists

The server rune-option table at `0x6ED510..0x719F10` is reserved by the
percentage-only portion of `rune_quality_factor`. The rune-upgrade server
table at `0x75797C..0x757DF0` is reserved by `rune_upgrade_discount` (`04.05`)
as well. Neither is a code cave.

Every hook the patch engine adds lives in a **code cave** carved out of
`libfwt_local_server.so`. Space in `.text` is the scarce resource:

- there is **no** zeroed or `NOP`-padded run ≥ 96 bytes in `.text`;
- the largest unclaimed byte run is **300 bytes** (`0xb45d34`), then 44 bytes;
- so every cave is cut out of code that is **provably unused** in this build.

The tool answers "which code is unused?" with four independent signals:

1. **direct calls** — `BL`/`B`/`B.cond` targets decoded with capstone;
2. **materialized addresses** — `adrp`+`add` pairs that build a function address
   (how a callback is handed to `dl_iterate_phdr`, `__cxa_atexit`, a thread, …);
3. **relocations** — `R_AARCH64_RELATIVE` addends and internal `JUMP_SLOT`
   symbols, i.e. function pointers stored in data;
4. **exports** — anything in `.dynsym` can be resolved by name, so it is never a
   candidate.

Reachability is a BFS over that graph. Anything never reached is a candidate.

## What the map sees (reference build `03ec76a1…`)

- `.text` at `0x7dac80`, 3,584,488 bytes, **3,967** functions with a size
  (1,501 exported in `.dynsym`).
- 12,166 direct call edges; 1,607 relocated pointers into `.text`; 13 addresses
  materialized with `adrp`+`add`; 0 pointer literals without relocations.
- 3,915 functions are reachable with **nothing** assumed dead.

Only 31 functions (28,564 B) are unreachable without assumptions — and that list
is **not trustworthy**: it is dominated by the offline APK author's own native
patching framework (`patch_offline_convenience_flow` 13,120 B,
`activate_strong_network_boundary_after_unity_ready`, `patch_module_connect_imports`,
`patch_words`, `install_runtime_callback_hook`, …). That code demonstrably runs —
it is what makes the offline APK work — so the reachability model is incomplete for
runtime-registered callbacks. **Treat those as false positives until a trap proves
otherwise.**

### Writable Scratch Slots

- `0xB2A13C..0xB2A164` (40 B inside `DEV_LOG_CAVE_VADDR`): dev magic bytes, hit
  counter, marker flag, start `cntvct_el0`, dispatch `sret`, and `DEV_DUMP` flag
  (page `0xB2A000` is flipped `PROT_READ|PROT_WRITE|PROT_EXEC` at runtime when
  needed).
- Page `0xBE2000` (`.data`/`.bss` RW page):
  - `0xBE2CBC` (4 B) & `0xBE2F14` (4 B): `recycle_hammer_rewards` reward selector
    and captured grade (zero-filled `.data` alignment gaps checked against
    adjacent globals and other scratch slots by `validate_cave_layout()`).
  - `0xBE2F68` (4 B) & `0xBE2F6C` (4 B): `rune_box_random_roll` roll counter and
    xorshift32 seed (8-byte alignment gap between `.data` end `0xBE2F68` and
    `.bss` start `0xBE2F70`).
- `0xBE3798` (8 B): cached `libil2cpp.so` base address written by
  `patch_offline_convenience_flow` and read by `battle_arena_save_fix` /
  `guild_raid_mercenary`.
- `0xBE62C8..0xBE62D8` (16 B, mapped RW page tail right after
  `alex_awakening_scratch`, beyond the last PT_LOAD `p_memsz` and outside
  every symbol): `guild_raid_skill_turn_gate` per-battle state
  (`{GameStage instance, currentTurnNo, cast bitmask}`).

Two very different bets:

- the **C++ demangler** is only used when something throws or prints a `typeid`;
  the game never does → the whole `itanium_demangle` family is fair game;
- the **on-device HTTP server** is only dead because LAN mode `NOP`s its spawn
  sites — in the default offline build that server *is* the game's backend.

## How to use it

```bash
# regenerate (≈15 s)
.venv/bin/python tools/dead_code_map.py --top 25 --json /tmp/caves.json

# render an existing report without re-analysing
.venv/bin/python tools/dead_code_map.py --from-json /tmp/caves.json

# custom assumption, e.g. "the Korean localization path never runs"
.venv/bin/python tools/dead_code_map.py \
    --profile korean=*korean* --json /tmp/caves.json
```

All currently allocated ranges listed in the **Allocated Code Caves & Scratch
Layout** table above are checked by `validate_cave_layout()` in
`core/core_patches.py` and must not be reused.

## Validating a candidate on the device

```bash
# 1. back up the save first — a SIGTRAP during a state write could corrupt it
.venv/bin/python fwt_patcher.py --backup

# 2. build a laboratory APK that traps the candidate (brk #0) and is debuggable
.venv/bin/python tools/lab_trap_apk.py --trap 0xb29ebc -o output/FWT-lab-dev.apk

# 3. install, then play the full route: lobby → shop → gem → arena → stage → battle
adb install -r output/FWT-lab-dev.apk
adb logcat -c && adb shell monkey -p com.nexon.fwar 1 >/dev/null   # or tap it

# 4. afterwards: alive means the region is dead in practice
adb shell pidof com.nexon.fwar
adb logcat -d | grep -iE "SIGTRAP|Fatal signal|DEBUG.*signal"
```

A crash means the region is alive — discard the candidate and note it here. A full
session with the process alive confirms the region for a real cave. `brk #0` is
used rather than a silent byte change because a wrong guess must fail loudly.

## Available Headroom for Future Caves

Both `dev_dispatch_log` (`0xB29EBC..0xB2A1BC`) and `dev_handler_timing`
(`0xB2A1BC..0xB2A35C`) are shipped, while `itanium_demangle::NewExpr::printLeft`
(`0xB33314..0xB3384C`) is completely full. Future hooks should target:

1. the remaining tail of `AbstractManglingParser::parseType`
   (`0xB2B068..0xB2B098`, **48 B** free after rune, costume package, equipment tier, Unknown Paradise daily scales, Fire Support, single Dragon Fang, Hero EXP cap, Absolute Protection persistence and Alex's Hero's Mark allocations);
2. the remaining tail of `AbstractManglingParser::parseUnnamedTypeName`
   (`0xB34F50..0xB34F78`, **40 B** after the Alex reservation);
3. the remaining tail of `AbstractManglingParser::parseEncoding`
   (`0xB30B14..0xB3101C`, **~1.3 KB** after `guild_raid_skill_turn_gate`);
4. other verified `demangler-only` candidates from `tools/dead_code_map.py`
   that do not overlap any range registered in `validate_cave_layout()`.

### Alex Awakening and Destiny Lance (12.01)

Feature `12.01` reserves `0xB2EA8C..0xB2FAA0` for client hooks,
`0xB34D44..0xB34F50` for evolution, skill costs and identity, and
`0xBE6268..0xBE62C8` for the extended writable runtime segment. The installer
chains from `0xAB3378`; each IL2CPP hook validates its original words.
`validate_cave_layout()` reserves these intervals against other features.

Trap testing on the reference release exercised startup and a battle for the
current client code bytes and `0xB34E64..0xB34F24`. The cost-row tail
`0xB34F24..0xB34F50` was not included in that session. The client and server
regions are only candidates under the demangler-excluded static profile;
surviving a normal session does not prove safety in error or unwind paths.

### Alex's Hero's Mark (12.03)

Feature `12.03` reserves `0xB2AFDC..0xB2B068` (140 B) for five
`fwt_valid_soulgear_idx::kIds` stubs and `0xB2FAA0..0xB2FBA0` (256 B, 255 B
used) for the client cave in the free tails of `parseType` and `parseExpr`.

- **Server side**: `fwt_valid_soulgear_idx::kIds` is inlined at five call sites
  (`0x7EBDEC`, `0x7EC814`, `0x8B08A4`, `0x9A027C`, `0xA1B42C`); each loop-exit
  branch is redirected to a 28-byte stub that also accepts the new mark id.
- **Client side**: the installer hooks `0xAB3304` — the `cbz w19` that splits
  the covault finalization flow's common exit path — and calls
  `PATCH_IL2CPP_HELPER` to replace the four-word prologue of
  `Skill::GetCurrentCoolTime` (client RVA `0x16064B4`) with an absolute
  trampoline into the cave payload. The installer constructs its trampoline on
  the stack and resolves the payload address at runtime so ASLR is respected.
  The payload reads the owner character's data container at offset `0x20`,
  consistent with the client's boss enumeration. The payload returns cooltime `0` when the
  active Soul Gear mark is level 10, otherwise replays the displaced prologue
  and continues at `0x16064C4`; its Soul Gear level offset remains unverified
  against a live object.
- `0xAB3304` was chosen after `0xAB337C` proved to collide with
  `battle_arena_save_fix` (25b): both features rewrote the same `add sp, sp,
  #0xc50`, so a combined build failed validation with `Unexpected Battle Arena
  late site 0xab337c`. `0xAB3304` is upstream of the whole epilogue chain and
  every boot passes through it in both directions, so the installer returns to
  `0xAB3308` when `w19 != 0` and branches to `0xAB335C` when `w19 == 0`. The
  block rewrites `x0`–`x5` immediately after the site, so the installer is free
  to clobber them and keeps only `x19`/`x20` (the two counters the flow carries)
  intact.
- The installer validates the stock `cbz` word (`d3020034`) before mutating and
  the inspector checks the hook, both caves and all five server stubs.
  Instruction-level emulation covers both branch outcomes, the missing
  `libil2cpp` base skip, and stack balance.
